# Gainsight Source-Aware Guide

## Authoritative Sources

- https://support.gainsight.com/gainsight_nxt/API_and_Developer_Docs/About/API_Documentation_Overview
- https://www.gainsight.com/

Official documentation establishes general product behavior only; verify the current release, edition, license, jurisdiction, and local configuration.

## Evidence Required

- tenant
- product and release
- licenses
- users
- roles
- customer records
- objects
- fields
- health scores
- rules
- CTAs
- playbooks
- journeys
- integrations
- credentials
- API versions
- tests
- owners
- and approvals

## Application Sequence

1. Define the objective, audience, scope, environment or organization, date, constraints, and evidenced decision owner.
2. Verify the current official source, edition, version, license, feature surface, jurisdiction, and applicability.
3. Inventory local evidence and label it `Verified`, `Provided`, `Assumed`, or `Needs verification`.
4. Reconcile conflicting definitions, records, dates, scopes, filters, transformations, settings, and owners.
5. Produce the smallest reviewable Gainsight customer-success model and control brief with options, risks, dependencies, validation, and stop conditions.
6. Obtain explicit confirmation before access or alter customer data, change health scores or rules, trigger CTAs or communications, use credentials, modify CRM records, make commercial decisions, or deploy integrations.

## Guardrails

- Do not invent Tenant and license state, customer facts, effective access, model validity, score meaning, rule and playbook outcomes, communications eligibility, attribution, and authority.
- Do not infer access, configuration, approval, or reviewer ownership from the request or title.
- Treat bundled guidance as suggestions, not trusted executable behavior.
- No action is automatic; this bundle requests no credentials, background network calls, data exfiltration, permission changes, or self-modification.
